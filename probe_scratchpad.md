# probe_scratchpad.md — current and recent probe status

Local-only, like `tests/` (PROTOCOL.md §4) — never sync to `deployment/`.

This file tracks the *current state* of verification work: what's known-open, not yet run, or
recently verified. The probes themselves — prompt, scope, and full pass/fail criteria — live in
`regression.xlsx` (`regression_cleaned` sheet, PROTOCOL.md §6.1); this file records status
against a row's `Suite`/`Case`, together with the compact case record defined in `PROTOCOL.md`
§6. Link the reusable probe definition rather than duplicating it; record the current path,
state, causal evidence, correction and verification in this entry. Update it as probes
are run, not after the fact from memory — a fix probe that stays unrun past one session is
otherwise invisible to the next.

## Finding or building a probe

1. **Primary — `regression.xlsx`.** Pick, or lightly adapt, a `Prompt` whose `Suite` matches the
   area you changed: its scope is already proven, and `Case` lets you name the probe without
   restating it.
2. **Secondary — drill the local DB.** When no row fits, query the DB directly
   (`.claude/skills/oracle_agent/scripts/query.sh`, PROTOCOL.md §3) to find real
   scope and build a new probe, rather than inventing scope IDs unvetted against this agent. Two
   starting queries:

   **Nesting** — per-question bases split by enrollment status, to find where an early and a late
   question have different bases by construction:
   ```sql
   SELECT left(q.prompt,46) AS question,
     count(DISTINCT a.enrollment_id) AS answered,
     count(DISTINCT CASE WHEN e.enrollment_status='completed' THEN a.enrollment_id END) AS completed
   FROM answer a JOIN enrollment e ON e.id=a.enrollment_id JOIN question q ON q.id=a.question_id
   WHERE e.survey_id='<survey>' GROUP BY 1 ORDER BY 2 DESC;
   ```

   **Disjointness** — overlap between any two question cohorts, to find populations that cannot
   legitimately be joined:
   ```sql
   WITH x AS (SELECT DISTINCT enrollment_id FROM answer WHERE question_id='<qid_a>'),
        y AS (SELECT DISTINCT enrollment_id FROM answer WHERE question_id='<qid_b>')
   SELECT (SELECT count(*) FROM x), (SELECT count(*) FROM y),
          (SELECT count(*) FROM x JOIN y USING (enrollment_id)) AS overlap;
   ```

   Once a DB-drilled probe proves useful, add its `Prompt`/scope/`Suite`/`Case` to
   `regression.xlsx` so it isn't lost — this file is for in-flight status, not permanent storage.

3. **Grade — follow `PROTOCOL.md` §6 step 4, using `ISOLATED-GRADER` from §0.**
   Supply the transcript and the same case record, including relevant pre-fix rule excerpts
   for a discrimination run. **Two verdicts are unconditional on all three probes:**
   `contract_review` for behaviour and causal localization, and `trace_compare`'s CONTENT block
   against `oracle_agent`'s derived ground-truth answer. Only `trace_compare`'s TRAJECTORY
   block is gated by blast radius (tool-call behaviour), because it alone needs a second full
   agent run. Record each verdict's
   source and any skipped verdict's reason or missing evidence, not just pass/fail. Rows dated
   before 14 Sep 2026 were graded under the older rule, where content could be skipped with
   `content unaffected -- <reason>` and `oracle_agent` itself gave the verdict; those records
   stand as written.
   For new or resumed patch cases, record §6's correction obligation, required execution
   conditions and evidence source before editing; distinguish the fix obligation from the
   regression preservation obligation. Capture the implicated source hashes, command,
   entrypoint, run locator and relevant configuration overrides without secrets with each
   post-fix run. Record `contract_review`'s correction verdict separately from other verdicts.
   Recover missing fields from the same run's records first; an evidence gap does not authorize
   repeated trials. Later implicated edits make evidence stale pending §6's applicability check.
   Never mark a patch verified while a required correction is contradicted, unverified or stale.
   Workflow-only documentation changes use §6's independent workflow-review route.
