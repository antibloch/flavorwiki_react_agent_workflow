# Frontend–Agent Streaming Contract

This document describes the current frontend contract for the agent API. The frontend communicates with the agent using `POST /ask` and receives newline-delimited JSON (NDJSON) events.

## 1. Authentication and request

```http
POST /ask HTTP/1.1
Authorization: Bearer <API_SECRET>
Content-Type: application/json
Accept: application/x-ndjson
X-Request-ID: <optional client-generated ID>
```

Request body:

```json
{
  "prompt": "Summarize the results of this survey",
  "survey_id": "c07b2733-c9fa-4a28-aa41-362d3f952517",
  "thread_id": "<optional existing thread ID>",
  "no_inventory": false
}
```

Required:

- `prompt`: non-empty user message.
- `survey_id`: survey being discussed.

Optional:

- `thread_id`: use the returned thread ID for subsequent turns in the same conversation.
- `no_inventory`: skips inventory loading when explicitly required by the application.
- `X-Request-ID`: client correlation ID. If omitted, the server generates one.

`client_id` and `org_id` are server-authenticated values and should normally not be sent by the frontend.

## 2. HTTP response

Successful requests return:

```http
HTTP/1.1 200 OK
Content-Type: application/x-ndjson
X-Request-ID: <request ID>
Cache-Control: no-cache
X-Accel-Buffering: no
```

The body is a stream of JSON objects separated by `\n`. It is not one JSON array, one JSON object, or an SSE stream. The frontend must parse it incrementally as bytes arrive.

Every event contains `request_id`, either supplied by the client or generated by the server.

## 3. Stream events

| Event | Meaning | Frontend action |
|---|---|---|
| `status` | Progress such as `scope`, `inventory`, or `running`. | Show progress if desired; do not treat it as answer text. |
| `token` | A streamed answer fragment in `text`. | Append to the current answer buffer. |
| `reset` | The agent is replacing an earlier intermediate answer, normally after tool use. | Clear the answer buffer and continue. |
| `tool_result` | Tool progress metadata. | Log or display progress; do not append it as answer text. |
| `heartbeat` | Keep-alive while the agent is waiting for model/graph work. | Ignore for rendering and keep the request open. |
| `done` | Successful terminal event. | Use `answer` as the authoritative final answer and stop reading. |
| `error` | Failed terminal event. | Show the server error and stop reading. |

Example events:

```json
{"type":"status","stage":"running","request_id":"..."}
{"type":"heartbeat","elapsed_ms":15000,"request_id":"..."}
{"type":"token","text":"The survey shows ...","request_id":"..."}
{"type":"done","answer":"The survey shows ...","thread_id":"...","telemetry":{},"request_id":"..."}
```

The event type is the discriminator. Unknown event types must be ignored for forward compatibility; they must not be converted into a network error.

## 4. `done.telemetry`

The successful `done` event includes server-side instrumentation. Values can be `null` when the model provider does not return a measurement.

Important fields include:

```json
{
  "request_id": "...",
  "turn": 1,
  "lock_wait_ms": 0.01,
  "scope_ms": 0.2,
  "inventory_ms": 22.3,
  "graph_ms": 34072.0,
  "llm_total_ms": 34059.5,
  "llm_turn_count": 1,
  "final_response_ttft_ms": 10167.9,
  "final_response_ttft_from_final_turn_ms": 10135.3,
  "final_response_generation_ms": 23900.0,
  "final_response_output_tokens": 3295,
  "total_agent_output_tokens": 3295,
  "first_llm_input_tokens": 37332,
  "first_llm_cached_input_tokens": 36352,
  "first_llm_uncached_input_tokens": 980,
  "tool_total_ms": 0.0,
  "tool_call_count": 0,
  "max_silent_gap_ms": 13634.0,
  "server_stream_total_ms": 34101.9,
  "completed": true,
  "client_disconnected": false,

```

The server-side `final_response_ttft_ms` is the authoritative agent TTFT measurement. It is measured from the final model call until the first final-answer token, and is distinct from the frontend's network-observed timing.

## 5. Frontend parsing requirements

The frontend should implement the following behavior:

1. Start the timer immediately before `fetch`.
2. Record the response-header time when `fetch` resolves.
3. Read `response.body` with a stream reader and decode incrementally.
4. Buffer incomplete chunks until a newline is received.
5. Parse each complete non-empty line independently with `JSON.parse`.
6. Record first byte, first event, first token, last event, and disconnect/error times.
7. Treat `heartbeat`, `status`, `tool_result`, and unknown events as valid non-terminal events.
8. Treat only `done`, `error`, an HTTP failure, or a read/parser failure as terminal.
9. On `reset`, clear the visible answer buffer before appending later `token` events.
10. On `done`, render `done.answer`; do not reconstruct the final answer solely from earlier token events.

Do not call `response.json()`, because the response is a stream. Do not use an idle timeout shorter than the expected silent model period.

Minimal parsing shape:

```javascript
const response = await fetch(`${API_BASE}/ask`, {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${API_SECRET}`,
    "Content-Type": "application/json",
    "Accept": "application/x-ndjson",
    "X-Request-ID": requestId
  },
  body: JSON.stringify({ prompt, survey_id, thread_id })
});

if (!response.ok || !response.body) {
  throw new Error(`HTTP ${response.status}`);
}

const reader = response.body.getReader();
const decoder = new TextDecoder();
let pending = "";
let answer = "";

for (;;) {
  const { value, done: streamDone } = await reader.read();
  if (streamDone) break;
  pending += decoder.decode(value, { stream: true });

  const lines = pending.split("\n");
  pending = lines.pop();

  for (const line of lines) {
    if (!line.trim()) continue;
    const event = JSON.parse(line);

    if (event.type === "heartbeat" || event.type === "status" ||
        event.type === "tool_result") continue;
    if (event.type === "reset") { answer = ""; continue; }
    if (event.type === "token") { answer += event.text || ""; continue; }
    if (event.type === "done") { render(event.answer); return; }
    if (event.type === "error") { throw new Error(event.error || "Agent error"); }
    // Unknown event: ignore and continue.
  }
}

throw new Error("Stream ended before done or error");
```

Production code should also flush `pending` after the reader finishes if it contains a final complete JSON line.

## 6. Client timing telemetry

After a completed request, or best-effort after a transport/parser failure, the frontend may report its measurements to:

```http
POST /threads/{thread_id}/telemetry?survey_id=<survey ID>
Authorization: Bearer <API_SECRET>
Content-Type: application/json
```

Body:

```json
{
  "request_id": "...",
  "turn": 1,
  "response_headers_ms": 12.4,
  "first_byte_ms": 13.1,
  "first_status_ms": 14.0,
  "first_token_ms": 5387.4,
  "last_event_ms": 20926.5,
  "done_ms": 20926.5,
  "client_total_ms": 20927.0,
  "last_event_type": "done",
  "client_error_type": null,
  "client_error_message": null
}
```

For a network/parser failure, send the measurements that exist, set `last_event_type` to the last received event type, and populate `client_error_type` and `client_error_message`. The last received NDJSON event should also be retained in the frontend's diagnostic record when available.

`turn` is the frontend's 1-based conversation-round counter. `thread_id` comes from the successful `done` event or the existing conversation state.

Telemetry is diagnostic only; failure to submit it must not replace the original agent result or error.

## 7. Timeout, proxy, and retry rules

- The server emits a heartbeat approximately every 15 seconds while waiting for graph/model work. The frontend and every proxy must allow an idle period comfortably above 15 seconds; a 30-second minimum is recommended.
- Configure reverse proxies to stream immediately, with buffering disabled for `/ask` (for example, Nginx `proxy_buffering off`).
- A total request timeout must accommodate long model responses and should be configured separately from the idle timeout.
- A heartbeat is not evidence that the answer is ready and must not reset the answer buffer.
- A stream that ends without `done` or `error` is a transport failure, not a successful empty answer.
- Do not show “network error” for a valid heartbeat, status, tool, or unknown event.
- A retry after a transport failure should preserve the diagnostic request ID and last event in telemetry. Because `/ask` is not idempotent, the UI should not blindly replay the same turn unless the application explicitly accepts a possible duplicate/continued conversation.

## 8. Error classification

The frontend should distinguish:

- HTTP/authentication failure: no valid stream was established.
- Server `error` event: the server ran and reported an agent/application failure.
- Parser failure: malformed or unexpected data was received.
- Reader/network failure: the stream disconnected before a terminal event.
- Timeout: the frontend or proxy stopped waiting before the server completed.

All classifications should include the request ID, thread ID when known, timestamps, last event type, and the last received event for diagnosis.
